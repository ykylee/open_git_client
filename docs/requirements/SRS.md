## 문서 목적

## 현재 상태
- 기준 시점에 Git 클라이언트 제품 컨셉, 성능 우선순위, 플랫폼 및 기술 제약, 선택된 개발 환경 요구사항이 등록되었다.
- 현재 SRS는 하이레벨 컨셉과 GitKraken 공식 문서 분석으로부터 도출한 초기 시스템 요구사항을 포함한다.

## 시스템 요구사항

### SRS-001 Git 클라이언트 기능 제공
- 시스템은 Git 저장소를 대상으로 동작하는 클라이언트 애플리케이션이어야 한다.
- 시스템은 Git 작업을 수행하고 그 결과를 사용자에게 제공할 수 있는 구조를 가져야 한다.

### SRS-002 참고 제품 기반 상세화
- 시스템의 정보 구조, 작업 흐름, 화면 구성은 `GitKraken`을 참고해 후속 요구사항으로 구체화할 수 있어야 한다.
- 단, 현재 단계에서는 특정 화면이나 기능 목록을 확정하지 않는다.

### SRS-003 Git 작업 성능 우선 설계
- 시스템은 Git 관련 작업의 실행 속도와 응답성을 최우선 비기능 목표로 삼아야 한다.
- 시스템 구조와 기술 선택은 Git 작업 처리 지연을 최소화하는 방향이어야 한다.

### SRS-004 비차단 처리
- 시스템은 시간이 걸리는 Git 작업 수행 중에도 사용자 인터페이스 또는 호출 흐름이 불필요하게 장시간 차단되지 않도록 설계되어야 한다.

### SRS-005 성능 검증 가능성
- 시스템은 Git 작업 성능을 측정하고 비교할 수 있도록 성능 검증 기준을 후속 요구사항으로 정의할 수 있어야 한다.

### SRS-006 Windows 대상 실행 환경
- 시스템은 Windows 환경에서 실행되는 클라이언트 애플리케이션으로 제공되어야 한다.

### SRS-007 Linux 빌드 가능성
- 시스템의 소스 코드는 Linux 환경에서 빌드 가능한 구조와 도구 체계를 가져야 한다.

### SRS-008 기술 선택 제외 조건
- 시스템은 MFC를 사용하지 않아야 한다.
- 시스템은 C#을 사용하지 않아야 한다.

### SRS-009 구현 언어 및 UI 프레임워크
- 시스템의 주 구현 언어는 `C++20`이어야 한다.
- 데스크톱 사용자 인터페이스는 `Qt 6` 기반이어야 한다.

### SRS-010 빌드 시스템
- 시스템은 `CMake` 프로젝트 구조를 사용해야 한다.
- 기본 빌드 실행 경로는 `Ninja` 생성기를 기준으로 구성해야 한다.

### SRS-011 Git 연동 방식
- 시스템은 `libgit2`를 기본 Git 연동 계층으로 사용해야 한다.
- 호환성 또는 기능 완전성이 필요한 작업은 네이티브 `git` 명령 호출 계층을 병행할 수 있어야 한다.

### SRS-012 Windows 개발 도구 체계
- Windows 주 개발 환경은 `MinGW-w64`를 기준으로 유지해야 한다.

### SRS-013 Linux 빌드 도구 체계
- Linux 빌드 환경은 `GCC` 또는 `Clang`을 사용할 수 있어야 한다.

### SRS-014 저장소 수명주기 관리
- 시스템은 로컬 저장소 열기, 원격 저장소 복제, 신규 저장소 초기화 기능을 제공해야 한다.
- 시스템은 여러 저장소를 빠르게 전환할 수 있는 다중 저장소 탐색 구조를 제공해야 한다.

### SRS-015 커밋 그래프 및 참조 시각화
- 시스템은 브랜치, 머지 관계, 태그, 원격 참조를 포함하는 Git DAG를 시각적으로 표시해야 한다.
- 시스템은 커밋 선택 시 해당 커밋의 메타데이터와 변경 내용을 탐색할 수 있어야 한다.

### SRS-016 작업 트리 및 선택적 스테이징
- 시스템은 작업 디렉터리 변경을 스테이징 전/후 상태로 구분해 표시해야 한다.
- 시스템은 파일 단위 스테이징과 전체 스테이징을 지원해야 한다.
- 시스템은 라인 또는 hunk 단위의 선택적 스테이징을 지원해야 한다.

### SRS-017 커밋 작성 및 이력 수정
- 시스템은 요약과 상세 설명을 포함하는 커밋 작성 기능을 제공해야 한다.
- 시스템은 마지막 커밋 amend를 지원해야 한다.
- 시스템은 revert, soft reset, mixed reset, hard reset 기능을 제공해야 한다.

### SRS-018 안전 복구 조작
- 시스템은 되돌릴 수 있는 로컬 Git 작업에 대해 undo/redo 기능을 제공해야 한다.
- 최소한 checkout, commit, discard, branch delete, remote remove, branch reset 작업은 복구 가능 대상이어야 한다.

### SRS-019 브랜치 관리
- 시스템은 임의 커밋 기준 브랜치 생성 기능을 제공해야 한다.
- 시스템은 브랜치 checkout, rename, delete 기능을 제공해야 한다.

### SRS-020 머지, 리베이스, 충돌 해결
- 시스템은 브랜치 간 merge와 rebase 작업을 앱 내부에서 수행할 수 있어야 한다.
- 시스템은 충돌 발생 시 충돌 파일 탐지와 해결 편집 흐름을 제공해야 한다.

### SRS-021 원격 저장소 동기화
- 시스템은 원격 저장소 추가 및 관리 기능을 제공해야 한다.
- 시스템은 fetch, push, pull 기능을 제공해야 한다.
- 시스템은 pull 전략으로 fast-forward, fast-forward only, rebase 방식을 지원해야 한다.

### SRS-022 검색 및 그래프 집중 보기
- 시스템은 커밋 메시지, SHA, 작성자 기준 커밋 검색 기능을 제공해야 한다.
- 시스템은 브랜치, 원격, 태그, stash를 숨기거나 선택적으로 강조해 그래프를 집중해서 볼 수 있어야 한다.

### SRS-023 변경 비교 및 파일 이력 탐색
- 시스템은 스테이징 영역과 커밋 비교에서 diff 보기를 제공해야 한다.
- 시스템은 파일 단위 이력 조회와 blame 성격의 변경 추적 기능을 제공해야 한다.

### SRS-024 대용량 저장소 대응
- 시스템은 대용량 저장소에서 초기 그래프 로딩 범위를 제한하거나 설정 가능해야 한다.
- 시스템은 더 깊은 이력 조회와 검색 결과 확장을 점진적으로 수행할 수 있어야 한다.
- 시스템은 위 동작을 UI 차단 없이 백그라운드로 수행해야 한다.

### SRS-025 코드 호스팅 서비스 연동 확장성
- 시스템은 향후 GitHub, GitLab, Bitbucket, Azure DevOps와의 연동 기능을 추가할 수 있는 구조를 가져야 한다.
- 연동 기능이 도입되면 pull request 또는 merge request 생성·조회·관리 흐름을 수용할 수 있어야 한다.

### SRS-026 서브모듈 확장성
- 시스템은 향후 Git submodule 추가, 초기화, 갱신, 상태 표시 기능을 추가할 수 있는 구조를 가져야 한다.

### SRS-027 Git LFS 확장성
- 시스템은 향후 Git LFS 초기화, 추적 패턴 관리, 관련 상태 표시 기능을 추가할 수 있는 구조를 가져야 한다.

## 갱신 규칙
- `CRS.md`에 신규 요구사항이 등록되거나 기존 요구사항이 수정되면 변경 내용을 분석한다.
- 분석 결과를 바탕으로 SRS 항목을 추가하거나 수정한다.
- 추적성 매핑은 CRS 식별자와 SRS 식별자를 연결하는 형태로 유지한다.
